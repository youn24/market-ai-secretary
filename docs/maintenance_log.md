### 調査の詳細

今回の「公開レポートが更新されない」は、これまでの事故（2026-08-18・2026-08-11など）とは**違う形**だった。
過去はコードが例外を握りつぶしたり `git add` が途中で失敗したりして「生成はしたが公開されない」形だったが、
今回は **GitHub Actions 側が `daily_report.yml` の予約実行そのものを一度も発火していない**。

- `daily_report.yml` の最後の実行は run #246（`2026-11-20T04:03:15Z` 完了）。これは実際には
  前日木曜 UTC（JST金曜の分）の3つの予約（21:23/22:23/23:23 UTC）が数時間遅れてまとめて走った結果で、
  本来の狙い通り3回のうち成功した分がガードで絞られている（正常な遅延パターン）。
- `cron` は `23 21/22/23 * * 0-4`（UTC日〜木 = JST月〜金）なので、金曜(UTC)・土曜(UTC)に発火しないのは正しい。
  問題は **日曜(UTC)＝今日の分（JST月曜の朝レポート）が、3回の予約時刻（21:23/22:23/23:23 UTC）を
  すべて過ぎた時点（確認時刻: 2026-11-22T23:38 UTC / 2026-11-23 08:38 JST）で1件も起動していないこと**。
  GitHub Actions の実行一覧（`actions_list` API）上、`daily_report.yml` に該当する `created_at` が
  Nov 20 以降1件も存在しない。
- 同じリポジトリの他の予約ワークフロー（`fx_noon.yml`・`weekly_report.yml`・`cot_weekly.yml`・
  `evening_recap.yml`）は同じ期間中（Nov 21〜22）に予定通り発火・成功しており、
  **GitHub全体やリポジトリ全体の障害ではなく `daily_report.yml` に限定された欠落**に見える。
  `health_check.yml`（UTC Mon-Fri 00:30のみ）は今日(UTC日曜)がそもそも対象外の日なので、
  今日発火していないのは正常（当初これも異常かと疑ったが cron の曜日条件を再確認して正常と判断した）。
- ワークフローの `state` は API 上 `active`。直近のワークフロー編集（`214ca2d` 鍵の配線修正）後も
  run #244〜246 は問題なく発火・成功しているため、YAML自体の構文や設定が原因とは考えにくい。

**結論（仮説）**: GitHub Actions のスケジューラが、今日分の3回の予約発火を取りこぼした
（CLAUDE.mdに記録済みの "2026-08-28 は実行そのものが行われなかった" と同種の、GitHub側の既知の信頼性問題）。
このリポジトリのコード（`cloud_run.py` / `src/design_ai.py`）側に新たな不具合は見つからなかった
（直近の成功実行 #246 で Step 7a2 は正常にレポートを生成している）。

**今回あえて行わなかったこと**: `workflow_dispatch` でこの場から `daily_report.yml` を手動実行すれば
本日分のレポートは生成できる可能性が高いが、本番の Telegram・LINE・メール・X投稿まで実際に発火する
（この保守セッションには通知用の認証情報を置いていない＝リポジトリの記録で完結させる方針のため）。
影響範囲が外部の通知・投稿にまで及ぶ判断はオーナー自身が行うのが適切と考え、
ここでは原因の特定とログの記録のみにとどめた。オーナーが手動実行ボタンを押せば即座に解消する見込み。
